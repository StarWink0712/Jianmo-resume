# Windows / macOS 平台适配改造规划

日期：2026-10-02  
代码基点：`3fa5ec0`，已采用精简 TeX 安装的版本。  
性质：仅供后续手动实施与测试的规划；本文不代表 Windows 支持已经实现或验证。

## 1. 改造目标与边界

保持一个 Git 仓库、一套前端、一套后端业务逻辑和一种简历工程格式，只对操作系统相关能力分别实现。

- 首批目标：现有 macOS Apple Silicon，以及 Windows 11 x64；Windows 10 是否支持，在验证上游引擎与 Python 依赖后另行决定。
- 保留原有界面、简历管理、自动保存、模块与样式、头像裁剪、PDF 预览和工程备份，不同时改产品功能或迁移前端框架。
- 普通用户只需兼容的 Python 和少量启动命令，不要求完整 MacTeX/TeX Live、管理员权限、Windows 开发者模式、WSL 或 Docker。
- `.resume.zip` 可在两个系统间互相导入；现有简历数据不因改造被清空、覆盖或强制搬家。
- Windows ARM64、Intel Mac、Linux 和桌面安装包不纳入第一轮，避免一次扩展过多组合。
- 保留文件、网络隔离与编译超时保护，不能通过删除保护措施获得“Windows 能运行”的结果。

当前约 16.2 MB 的引擎下载量只对应 macOS。Windows 需要独立测量，不能直接沿用该数字。

## 4. 平台适配层的职责

不要把所有功能塞进一个巨大的“平台工具类”。可以先用少量模块函数或 Protocol 定义下列边界，不引入额外框架。

| 接口职责 | 输入 / 输出约定 |
| --- | --- |
| 平台识别 | 返回明确的平台键，如 `darwin-arm64`、`windows-x64`；不支持的平台明确报错 |
| 独占锁 | 接收规范化后的目录身份，返回可关闭的锁句柄；失败映射为现有“已有服务运行”等错误 |
| 私有目录准备 | 设置数据和作业目录的实际访问权限，不仅返回创建成功 |
| 编译环境构造 | 给定运行时与作业目录，返回经过筛选的环境变量和各个工具的绝对路径 |
| 工作目录字体准备 | 保持模板中的 `fonts/` 相对路径可用，不要求 Windows 创建软链接 |
| 受限进程执行 | 接收参数数组、工作目录、环境、读写范围、墙钟预算和资源策略；返回统一结果 |
| 本地监听配置 | 固定 loopback；按平台配置端口排他行为，重复启动必须可靠失败 |

建议执行结果至少区分：退出码、启动失败、墙钟超时、CPU 限制、内存限制、隔离初始化失败、耗时和进程树清理结果。无法准确归因时记录未知原因，不把所有失败都标记为超时。

执行器需要声明实际能力，例如内存是硬限制还是采样监测、文件输出是 OS 限制还是轮询限制。共享层判断必需能力是否满足，不假设 Windows 与 macOS 机制逐项相同。

共享编译流程仍按同一顺序执行：

```text
校验简历 -> 渲染可信 TeX -> 准备作业与字体
  -> 受限运行 XeTeX -> 受限运行 xdvipdfmx
  -> 检查文字、字体、页数与溢出 -> 返回 PDF
```

两个编译阶段共用剩余墙钟预算；异常、取消和退出都必须清理整个相关进程树。不要在多线程 FastAPI 服务中重新引入 Python `preexec_fn`。

## 5. 先解决导入链，而不是先换命令

当前 `backend.compiler` 从 `experiments.m1.run` 导入 `compact`、`expected_text`，该模块顶层导入 `fcntl`。`scripts.light_runtime` 又导入 `packaged_cli`、`runtime` 和基线验证函数。这意味着 Windows 可能在执行任何 TeX 命令之前就导入失败。

第一批工作应拆出 `compact`、`expected_text`、样例判定和基准判定等纯逻辑，让后端、资源验证与自检不再导入完整实验脚本。`render.py`、`fonts.py`、`pdf_checks.py` 中可共用的代码可逐步迁移，先保留兼容导出，减少一次性修改。

验收要求是正式后端、安装器和共享测试在 Windows 上均可正常导入；不能靠把整个 Windows 测试集跳过来通过这一关。

## 6. Windows 精简 TeX 运行时

### 6.1 资源选择

沿用当前 XeTeX / xdvipdfmx 排版路线，不在本次改造中同时更换为另一套排版引擎。

1. 查找并下载真实存在的 Windows x64 上游包，核验包来源、版本、平台与文件清单；不要从 Mac 包名推测下载 URL。
2. 找到等价的 XeLaTeX 格式调用方式。上游可能使用 `xetex.exe` 加 `-fmt` / `-progname`，也可能提供其他启动入口，必须通过实际包验证。
3. 清点 EXE 的 DLL 依赖，包括递归依赖及动态加载项，结合 PE 导入表、运行观察和隔离环境验证，不仅复制两个 `.exe`。
4. 按文件锁定必要的 EXE、DLL、配置、字体和 CMap；排除未使用的工具、完整发行版和文档集合，保留许可与必要源码说明。
5. 在没有全局 TeX 的 Windows 上验证真实 PDF，测量下载和磁盘占用后再写入 README。

当前共用支持包是从 macOS 基线生成的，不应直接宣称可原样用于 Windows。对宏包、格式输入和默认配置逐项比较，相同内容共用，不同内容归入平台覆盖资源。格式生成专用源码和许可材料继续放在日常 TeX 搜索目录之外。

### 6.2 校验与格式生成

- 包名、版本用于定位资源；压缩包及 EXE/DLL 哈希用于确认内容，不能只检查名称。
- 每个平台拥有自己的引擎哈希。Windows 引擎不与 macOS 引擎比较。
- `xelatex.fmt` 在目标平台根据批准的输入生成，只记录本次生成物的完整性，不比较两台电脑或两个系统的格式缓存哈希。
- 下载继续使用 HTTPS、固定版本、大小上限、哈希和可信后备源；失败不得改用未经验证的系统 TeX。
- 清单路径使用 `/`；计算文件哈希时保留原始字节，不通过转换换行来“修复”哈希不符。
- 调试二进制依赖时不要把完整系统 PATH 混入生产编译环境，否则有全局 TeX 的开发机可能掩盖缺失的 DLL。

### 6.3 安装与活动版本

建议两平台统一改为不可变版本目录加 `current.json`，代替依赖软链接的 `current`：

```text
local-install/
  releases/<platform>-<lock-digest>/
  current.json
```

`current.json` 只保存相对的版本目录、平台与锁摘要。读取时验证目录必须位于 `releases/` 内，拒绝绝对路径、目录穿越和重解析点逃逸。

安装事务按“加锁、下载校验、暂存解包、生成格式、PDF 自检、落定版本目录、替换活动记录”的顺序执行。活动记录写临时文件后在同一文件系统替换；Windows 读者及时关闭句柄，替换被占用时有限重试，失败保留旧记录。

macOS 迁移时先兼容读取旧 `current` 软链接，验证后再采用新记录，不删除旧版本。Windows 不尝试覆盖正在运行的 EXE/DLL；编译器持有已解析的不可变版本路径，旧版本延后清理。

运行时清单分开校验共用的内容哈希和平台专属的权限策略。不要拿 Windows 的 `st_mode` 与 macOS `0755` 做同一种完整性断言。

## 7. Windows 执行、隔离和资源限制

这是最需要先做原型验证的部分。**Job Object 管理进程与资源，不是文件或网络沙箱；restricted token 也不自动等于严格的目录白名单。**

### 7.1 进程与资源

- 为每个编译任务创建专用 Job Object，配置关闭 Job 时终止关联进程，以及合适的内存、CPU 和活动进程策略。
- 使用挂起创建进程、加入 Job、完成约束设置后再恢复的启动顺序，避免子进程在加入 Job 前逃逸。加入失败必须停止，不降级为裸进程。
- 墙钟超时由宿主用单调时钟监督，超时后终止 Job 并等待子进程退出。服务器崩溃、用户取消和 Ctrl+C 退出也必须验证清理效果。
- 区分 Job 的内存记账与 macOS RSS 采样，不把它们写成完全等价的测量。文件大小与磁盘输出另做限制，Job Object 本身不提供 POSIX `RLIMIT_FSIZE` 的等价能力。
- 只继承必要的日志/管道句柄，Job 管理句柄不传给编译器；验证在 CI 或已有父 Job 环境下的嵌套行为，不依赖任意 breakaway。
- `taskkill /T` 或 `psutil` 可以辅助诊断，不能作为唯一的进程树隔离和生命周期保证。

可用 Windows 专属 Python 依赖封装 Win32 API；若需要原生辅助程序，把它限定为小型可信启动器，不在其中复制简历业务。普通用户不能被要求现场安装 C++ 工具链；如分发辅助二进制，另外安排构建、来源校验和许可记录。

### 7.2 文件与网络隔离

优先验证可由普通用户启动的 AppContainer 路线，并配合必要的访问控制和 Job Object。不能在未经实测的情况下把它标记为已选定的可用实现。

- 编译子进程只获得所需运行时、字体和当前作业资源；简历数据库、其他简历作业、用户文档目录不授予访问。
- 不授予网络能力，不设置 loopback 豁免；分别测试 DNS、外网连接和本机网络，避免只测试一个命令就宣称禁网有效。
- 明确记录 AppContainer 默认可读的系统位置，验证实际访问范围，而不是假设所有目录天然都被拒绝。
- TeX 的 `-no-shell-escape`、`openin_any`、`openout_any`、可信模板和 Markdown 白名单继续保留，但不能替代 OS 隔离。
- 编译子进程和 HTTP 后端的权限必须分离：后端需要读写数据库并监听 loopback，TeX 子进程不需要这些权限。

如果该路线无法在目标 Windows 版本、普通用户账户和上游引擎下成立，暂停 Windows 正式发布并调整执行方案；不能静默关闭沙箱，也不能将要求 WSL 的方案宣传成原生 Windows 支持。

## 8. 文件锁、路径、字体与数据兼容

| 项目 | 实施要求 |
| --- | --- |
| 数据目录锁 / 安装锁 | macOS 保留 `flock`；Windows 使用经验证的原生文件锁或命名互斥量。锁的身份关联规范化目录，不仅关联进程 PID；异常退出后可重新获得锁 |
| Windows 权限 | `chmod(0600)` 不等于私有 ACL。数据目录权限需覆盖数据库、WAL、SHM、日志与备份；编译器身份只获当前作业的必要权限 |
| 字体目录 | 模板继续使用 `fonts/`。Windows 第一版可复制当前固定字体到作业目录，避免软链接权限；评估拷贝成本和清理。不要擅自改用系统字体 |
| 进程参数 | 始终使用参数数组与明确的工作目录，不经 shell 拼接用户内容；Windows 命令行引用交给经过验证的启动封装 |
| 环境变量 | 平台层分别构造必要环境；Windows 保留所需 `SystemRoot`、`WINDIR`、TEMP 等，不照搬 Unix 最小环境。PATH 列表使用系统分隔符 |
| DLL 搜索 | 仅加载批准的运行时 DLL 和必需系统库；防止从当前目录、任意 PATH 或用户写入位置误加载同名 DLL |
| 中文及特殊路径 | 测试中文用户名、空格、括号、`&` 等；文件系统路径、归档路径和 TeX 源码路径分开处理，不能全局将反斜杠替换为斜杠了事 |
| Windows 特殊路径 | 拒绝归档中的盘符/UNC、ADS、设备名、尾部空格/点、大小写碰撞及重解析点逃逸；单独评估长路径支持，不强迫普通用户修改系统注册表 |
| 数据与备份 | `.resume.zip` 的 JSON、头像和样式格式保持不变；跨系统迁移优先导入工程，不复制正在运行的 SQLite 数据文件 |
| 存储位置 | 首轮保留当前默认数据位置和 `--data-dir`。对只读目录明确报错；Program Files、网络共享盘、同步盘不在未测试时宣称支持 |
| PDF 缓存 | 编译指纹纳入平台、完整引擎/DLL 锁、模板与执行器实现；跨平台恢复后不把旧缓存当成新引擎的编译结果 |

## 9. 启动入口设计

保留 `scripts/start-local.sh`，增加 `scripts/start-local.ps1`。二者只负责找到兼容 Python 并转交共享启动器，下载、平台识别和运行时安装逻辑不要复制两遍。

Windows 需处理 Python Launcher `py`、明确指定的解释器以及 Microsoft Store 执行别名，验证实际版本和架构。虚拟环境路径为 `.venv/Scripts/python.exe`，不能调用 `.venv/bin/python`。无需激活虚拟环境即可运行解释器。

PowerShell 入口要检查每个原生命令的退出码，将参数按数组传递；不修改系统级执行策略，不要求以管理员身份运行。若脚本策略限制运行，应给出直接通过 Python 启动的替代入口。

以下是改造后的目标命令示意，文件尚未实现，不能现在加入 README 当成可用命令：

```powershell
# Windows：薄入口
.\scripts\start-local.ps1

# Windows：不依赖 PowerShell 脚本策略的目标替代入口
py -3 scripts/bootstrap.py
```

共享启动器应处理：平台检测、虚拟环境创建、公共及平台专属依赖安装、精简运行时安装、失败即停止、启动参数转发和退出清理。已经存在的依赖与运行时不重复下载，准备完成后支持断网启动。

## 10. 基线与证据迁移

当前 `implementation_hash()` 把文件路径和内容一起纳入证据。移动模块会触发证据过期；这是需要正式重验的变更，不是让新路径绕过校验的理由。

1. 先保存当前 macOS 基线和已通过记录，再调整摘要规则，覆盖新 `core/`、平台适配层及实际影响生成/执行的安装代码。
2. 摘要中的项目相对路径统一 `.as_posix()`，序列化格式固定；不要因 Windows 的反斜杠导致相同源码产生伪差异。
3. 将共享源资源、平台引擎及执行器证据分开标识。Windows 的 EXE/DLL、格式输入或配置发生真实差异时，逐项审核并形成独立平台基线。
4. 对改造后的 macOS 实现完整重跑，Windows 也独立执行对应实验。共享文件相同不代表 Windows 行为已经验证。
5. 历史证据需能区分源清单、实现版本与平台；只有源清单摘要的归档键不足以表达“源码资源相同、执行器已改变”。
6. 不手工替换报告哈希、复用旧平台的通过标记或删除失败检查。未测项目保持未验证。

不同平台生成的 PDF 不要求字节完全相同；时间戳、对象顺序等可能不同。跨平台验收应比较文字、字体、页数、链接和视觉布局。在同一平台内仍保留稳定样本和内容完整性检查。

## 11. 推荐实施顺序

| 步骤 | 主要工作 | 完成门槛 |
| --- | --- | --- |
| A. 固定现状 | 建立改造分支、保留当前源码/数据备份和 macOS 验证记录 | 有明确可回退版本；不改用户数据 |
| B. 提取共享纯逻辑 | 解开后端对实验工具和 Unix 模块的导入依赖 | Windows 可导入后端、安装器和共享测试；Mac 业务行为不变 |
| C. 提取 macOS 适配层 | 封装锁、进程、资源、沙箱、字体准备、路径和权限 | Mac 完整回归通过；Windows 分支不需要复制业务代码 |
| D. Windows 最小原型 | 验证引擎/DLL 闭包、中文 PDF、AppContainer、Job Object、普通用户权限 | 无全局 TeX 可编译；基本隔离与进程清理可行，先做这一步再投入完整安装器 |
| E. 安装与入口统一 | 平台锁、活动版本记录、清单、共享 bootstrap 和 Windows 入口 | 空环境安装可用；坏包/失败升级不会破坏旧版本；不依赖软链接或管理员权限 |
| F. 业务与故障验证 | Windows 完整操作，跨平台备份、异常退出、离线和路径测试 | 下面验收矩阵的必需项全部通过，Mac 同时回归 |
| G. 文档与交付 | 更新平台要求、实测体积、安装命令与验证结果 | 只描述已验证的平台；未满足安全门槛不宣布 Windows 支持 |

优先顺序是先消除导入障碍，再证明 Windows 编译与隔离可行，最后完善安装体验。不要先复制全部代码到 `windows/`，也不要先制作安装包再发现核心引擎不能受限运行。

## 12. 由实施者执行的验收清单

下表是待执行的验证，不是本次工作的测试结果。

| 类别 | 两个平台都必须验证的项目 |
| --- | --- |
| 启动 | 无系统 TeX、空 `.venv`、空运行时；依赖下载、格式生成、自检、主页可访问；端口占用时不接管已有服务 |

测试组织建议：共享行为用例在两边运行；OS 特有机制用对应平台用例覆盖。Windows 上可以跳过 `sandbox-exec` 的专属用例，但必须运行对应的 Windows 隔离用例，不能把安全要求整体跳过。至少使用真实 Windows 环境，WSL 不能替代原生 Windows 验收。

## 13. 最终交付与停止条件

后续实施完成后应得到：共享业务代码、两个平台适配实现、两份平台运行时锁、共用安装逻辑及两个启动入口、跨平台测试和各自结果、简洁准确的 README，以及原有工程格式兼容证明。

以下任一情况未解决，就不要将 Windows 标记为正式支持：依赖全局 TeX 或开发机私有 DLL、需要关闭沙箱、普通用户不能安装运行、编译子进程不能可靠终止、存在跨平台数据损坏，或只在 mock/WSL 中测试过。

本次仅编写此规划文档。代码改造、下载或安装新依赖、Windows 测试、Git 提交、打包和推送均留给后续实施者；不要把本文中的目标命令或验收清单当作已执行结果。
